# Pro 自动补货

与 Pro 管理同级的独立菜单，包含监控大屏、补货配置、兜底配置、决策与记录。“查看”打开详情弹窗，支持 Esc 关闭和焦点返回。原数量型定时任务的配置与计算公式保持原状，共享账号领取与卡片占用保护。

## 启用

手动全自动、单项开通与其银行卡列表，也按实际提交的 5x / 20x 套餐和所选卡台绑定开卡模板。只有原开卡记录匹配该模板及套餐的卡可参与；无匹配可用卡时，按对应模板和原自动补卡开关、预算准备新卡，不能借用另一套餐的旧卡。明确选择的错配卡在付款前拒绝。手动流程使用窗口显示的付款套餐，定时与补货仍使用各自分时规则。

手动全自动失败换号保存并沿用原模板；套餐、卡台或供应商参数变化时暂停等待核对，模板改成另一套餐时也拒绝继续。已经成功付款的原单恢复、查询和后续收尾不重新选卡或付款；银行卡管理的总列表仍保留所有卡。

1. 更新并部署 Space；数据库自动添加补货表，默认关闭、观察模式。
2. 在 Pro 管理配置 Sub2 推送、请求并发、开通工作并发、目标母号、供应商和卡片。
3. Sub2 开启实时监控即可，兼容 Qerkai-sub2api 现有接口，无需安装采集质量扩展。
4. 读取分组，单选推送目标中包含的监控组，使用不共享账号的专用组。
5. 先观察容量、消耗和实际就绪耗时，设置水位、批量、在途、预算、冷却，再切换自动执行。

后台达标后调用现有全自动 Pro：登录、付款、新授权、推送、额度巡检、合并及移出。浏览器关闭不影响运行。“立即评估”在自动模式下会执行符合规则的任务。同池旧定时任务仍会按原策略补货，页面提醒但不擅自关闭。

## 并发容量使用比例

“补货配置 → 基本设置 → 总并发容量使用比例（%）”默认 60%，可填写 1～100 的整数。现有配置没有该字段时也采用 60%。大屏有效容量＝监控组内可用账号的 Sub2 原始容量总和 × 使用比例，已用并发和等待数量保持真实值。触发数量＝有效容量 × 触发百分比，向下取整。例如原始 80、比例 60%，按 48 计算；触发阈值 70% 时 48 × 70%＝33.6，取 33，占用达到 33 即参与连续压力确认。低容量算出 0 时，空闲且无等待不会触发补货。

持续并发补货、退出前容量预测、新号与可预期在途的容量统一折算；总量保留小数，不逐账号取整。大屏展示原始容量和比例，历史决策保留当时的比例与有效容量。Sub2 原始数据与任务保存的原始容量不修改，比例变化不会重复折算；预计支撑时间仍只依赖 Sub2 的美元额度和消耗速度。

## 每日禁补时段

在“Pro 自动补货 → 补货配置 → 每日禁补时段”设置开关，并通过“添加时段”和“删除”管理多个开始/结束时间。原有单个时段自动保留为第一行；任一时段命中即禁补，重叠或首尾相接的时段连续生效，未命中任何时段时恢复判断。默认关闭；时间为北京时间（Asia/Shanghai / UTC+8），不依赖服务器或浏览器时区。支持同一天和跨午夜，例如 23:00～07:00；包含开始、不包含结束。启用时要求合法的 HH:mm，开始与结束不能相同，全天暂停请关闭自动补货总开关。

禁补期间继续采集、更新预测、记录决策和跟踪在途，但时间、并发、空组启动、最低备用、强制合并前接替与紧急排队均不能新增补货；“立即评估”也遵守此限制。决策、事务预留和最终派发分别检查当前时间，防止采集或排队期间跨入禁补窗口。已预留但未启动的任务在监控轮次中撤销，释放账号与预算；已启动的登录、开通、推送、原订单核验及后续流程继续执行。

结束时间后的下一轮检查，按新快照重新计算缺口，仍应用批量、冷却、在途、预算及失败保护，不积攒或一次性补齐禁补期间需求。大屏显示当前禁补状态，历史决策保存当时的配置及禁补原因。禁补仅限制 Pro 自动补货，不影响原定时任务或手动流程。

## 空组兜底调度

在“补货配置”右侧的“兜底配置”页签独立保存另一套 Sub2 地址、管理员邮箱／密码、一个 OpenAI 分组，以及多选的 OpenAI API Key / OAuth 账号。API Key / OAuth 是账号类型，不读取或展示账号密钥；管理员密码加密保存，留空保留，仅同地址同邮箱可复用。读取分组和账号是只读操作，启用保存时检查所选账号归属和类型。默认关闭，独立检查／失败重试周期默认 3 秒，可配置 2～300 秒。该周期不会修改“运行节奏”中的并发检查、额度刷新或补货冷却。

主监控来源沿用 Pro 推送的 Sub2 连接与自动补货选定的唯一监控组。全天按该组实际 OpenAI OAuth 账号数量切换（API Key 不计入）：0 个开启所选兜底账号，大于 0 个关闭。补货总开关、观察模式、每日禁补时间和 Pro 任务运行状态不参与兜底判断。登录、付款、授权、待推送的在途不算组内账号；账号真正入组后即在下一轮关闭兜底，不等待整批结束或额度刷新。每日禁补仍只限制新增补货。

独立后台循环直接使用原生分组和完整分页账号列表，不依赖额度或并发监控。正常以轮次开始时间计算周期，轮次不重叠；失败结束后等待配置秒数再重试。分组不存在、采集失败、超时、分页缺失或快照过期时保持当前调度，保留带时间戳的最近有效数据供查看，不把失败当空组。采集恢复后自动切换，也可“立即核验／重试”。重启先重新采集，不使用重启前快照决定开关。修改监控连接或组后，旧样本立即失效。

主组采集限时 5 秒；兜底逐号最多 8 个并发、每号 5 秒，一轮处理限时为两倍检查周期（最低 10 秒、最高 40 秒）。旧连接收尾排在当前所选账号之后；未完成账号在后续轮次继续核验。只在实际状态与目标不一致时调用现有 `POST /api/v1/admin/accounts/:id/schedulable`，不清除冷却、不修改分组、模型或凭据。修改前先持久化接管记录和意图，超时／响应未知保留记录，下轮先读真实状态再决定是否重写。

关闭兜底自身开关会关闭已接管账号；取消选择、更换连接后旧账号收尾关闭，核验成功后清理跟踪记录。相同端点更换管理员凭据不先关闭仍被选中的账号。已移出兜底分组的账号不会再次开启。大屏和配置页展示主监控组、采集账号数及时间、目标调度、逐号实际状态和错误。兜底配置独立保存，启用即接管所选账号，与补货观察模式无关。

按数量切换意味着禁用、冷却、无额度 OAuth 账号仍算组内账号，不等于可用容量。秒级轮询、接口耗时和 Sub2 自身调度缓存决定实际切换延迟，不能保证绝对无间隙；此功能不会建立两套 Sub2 之间的流量路由。

## 决策和到货延迟

时间不足、持续并发、最低备用、空分组启动与强制合并前接替独立判断，净缺口取最大值，再应用批量、在途、数量、预算、池上限与熔断。最低备用和空分组启动默认均为 0，保持已有配置行为。

“补货配置 → 补货数量 → 空分组启动补货数量”用于空池启动，0 关闭。只有账号和并发采集成功、快照有效且监控组 OpenAI OAuth 成员为 0 时触发（API Key 不计入）；组内有禁用、冷却或无额度 OAuth 账号不属于空组，成员类型不明确时不按空组触发。无需等待额度样本或并发连续确认。设置 3 且已有在途时先等待这一批完成，不追加批次；登录、开通、待推送、结果未知和超时无 ETA 的任务均占用本批，不能因尚未入组重复开通。

仅由空组规则触发时，不按普通最小批量向上取整（设 1 就按 1 计算），仍受每批最多、工作并发、最大在途、账号池、小时／日数量、预算、冷却及熔断限制。多个规则同时触发仍取最大缺口。观察模式只给建议；启用自动执行后才调用全自动 Pro。

本轮已原子预留的所有补货批次按工作并发逐个执行，首个账号入组不会取消本批剩余预留；采集异常暂停派发，配置变更或手动暂停会撤销未提交预留。组内有账号后，空组规则不再新建补货任务，因此不会持续维持固定数量。设置数量大于每批上限时，本轮只预留上限内数量；以后仅在仍为空组且冷却结束时重新计算缺口，不保证非空后继续补到启动数量。

状态为预留、启动确认、全自动执行、已推送待核验、就绪。逐号核验 Sub2 真实 ID、原分组、模型和可调度状态；无需等待整批或额度接口。已启动不等于当前容量，仅可信 ETA 的在途进入未来供给。

预计就绪覆盖工作排队、登录、开通、授权、推送和监控核验。历史足够时采用 P90，并按最新阶段的历史剩余耗时更新；不足时使用回退值。ETA 锚定原阶段时间，不随每轮检查向后漂移。超时任务保留在途但不承诺未来容量。提前补货取配置水位与保守到货时间加余量中的较大值。

每次只执行一批补货：本批无论 1 个还是多个账号，全部成功推送并经 Sub2 核验可调度后，再完成一轮新的有效监控采集，才根据当前需求判断下一批。等待期间不累积并发或退出压力确认次数；恢复后重新连续确认。紧急账号排队也不能绕过整批等待。需求回落或费用样本缺失不取消、不搁置本批排队任务；已预留任务按工作并发继续执行。暂停、配置变更、禁补时段及失败熔断仍生效。明确失败或取消的任务结束本次占用；付款未知、已付款但未推送完成的任务继续核验或续跑，不能作为成功到货放行下一批。排队任务不显示会不断后移的预计就绪时间。批次与结束时间持久化，重启后仍等待新监控数据。付款成功但授权中断时按原重试限制恢复登录和授权，不重复购买。结果未知保留订单、预算及在途，在 Pro 管理核验原订单。

第二步“开通”发生任何执行失败，统一领取一个未使用的新账号，从第一步登录开始，不在原账号重复开通。适用于自动补货、定时全自动及手动启动全自动。高级设置的“第二步失败换号次数”默认 2、范围 0～10，不含首次账号；0 表示失败停止。每条流程启动时固定上限，换号次数、前后账号与待领取状态持久保存，重启不会归零。没有新账号或可用银行卡时显示等待原因。补货接替仍计入开通次数、预算和并发，每次均经过原卡台准备及订单入场检查；不再叠加旧的一次风控替补规则。原账号、订单及不明付款占用保留，已确认成功不换号，手动停止取消整条换号链。窗口会跟进接替账号。第一步及第三步以后的错误沿用各自原规则，其他步骤重试次数不作用于第二步。单项开通按钮不是全自动流程，不自动扩展为完整全自动。

## 预计支撑时间与推送时限

监控大屏的预计支撑时间只使用 Sub2 监控组返回的账号、同套餐同窗口额度、消耗速度、重置、账号到期和并发数据。当前支撑时间不包含未就绪任务，不受 Pro 推送时限、开通供应商配置影响。以 15 秒步长估算首次供给缺口；套餐混用、窗口不同或样本不足时暂不可估。净补货需求计算可另外考虑套餐兼容且 ETA 可信的在途。

Pro 管理新增“推送时限”列：已开启及保存的分钟数、未开启、历史未知。新账号开始开通流程时保存当时开关和分钟数；仅首次成功推送开始倒计时，失败不开始，重推不重置。后续全局调整只影响新账号。历史账号没有保存该字段时不推断、不套用当前全局值，显示未知，不自动产生强制合并期限或提前补货需求。账号凭据更新及迁移保留已保存策略。

## 强制合并前提前补货

在原“补货配置”内与时间和并发规则并列设置，默认关闭、阈值 15 分钟。扫描当前监控组的全部账号；只统计通过 EJH 卡成功开通、已成功推送且仍可调度的 Pro 账号。已合并、已移出、已删除、未开通、时限未开启或记录未知的账号排除。

每号剩余分钟=max(0, 首次成功推送时间+账号保存的时限−当前时间)，平均值=剩余分钟总和÷有效账号数。平均值严格低于阈值才独立触发，不需要额度或并发规则同时满足。接替需求取逐号低于阈值的账号数，扣除已经关联的接替任务；与其他净需求取最大值，仍遵守批量、冷却、在途、预算及失败保护。建议阈值大于开通到可用耗时加缓冲。

每个原账号生命周期只关联一个接替任务，先关联目标一致的已有在途，再原子预留新任务。未知付款保留占用；确认失败或取消后才重新计算。重启以及 48 小时后仍保留就绪接替关系。新号成功推送且经 Sub2 核验可调度才算就绪。平均值回升或老号离组不会取消已安排的接替；配置变化、关闭规则或暂停仍会撤销未提交任务。

大屏“预计支撑时间”右侧显示平均剩余分钟、参与数、临期数、待补数、接替中和就绪数，并可展开逐账号倒计时。未开启及未知数量单列；采集不可用时隐藏旧统计，不用旧数据触发开通。

## Sub2 采集与故障恢复

Space 使用原生账号列表和并发接口，校验快照时效、分页完整性、组成员、容量及负载必要字段。`quality`、`load_known` 为可选增强信息，缺少时允许使用完整的原生数据；若明确报告采集失败，仍暂停新增。合法空组和零负载不会被当成采集失败。

请求失败、超时、关键字段缺失、快照过期或跨接口数据不一致时暂停新增，保留最近有效数据及其时间戳供查看，不用旧数据开通。总开关和运行模式保持不变，后台在每轮检查结束后等待配置的“并发检查周期”再重试；成功后自动恢复正常规则判断，连续压力确认重新积累，仍遵守冷却、预算和在途限制。已提交任务继续按原全自动流程执行和跟踪。

页面异常时显示“立即重试”，可主动发起一次新采集；成功才恢复判断，失败继续暂停并显示原因。已有采集或配置更新在进行时，提示稍后重试，不将旧数据冒充本次成功。手动关闭的总开关不会因重试成功而重新开启。额度独立采集仍按额度刷新周期运行，缺少可信额度样本时仅停用时间预测，并发规则仍可独立生效。

原生接口若将内部采集错误返回为正常的 0，Space 无法完全识别。历史质量扩展补丁仅作可选参考，不是启用前提，本次不修改或部署 Sub2。共享组账号及大面积账号异常仍按既有规则处理。

## 持久化及预算口径

SQLite 原子预留账号、预算与决策，派发前 CAS 领取；付款走原幂等机制。重启恢复跟踪。尚未提交下游创建请求的账号，在推送时读取最新保存的推送配置（包括绑定代理开关、候选代理、分组、模型、并发和优先级）。同一站点保留原购买时段的额外分组，切换站点不携带旧分组。实际推送目标加密保存，创建结果不明时沿用原站点、请求、代理及幂等键；已推送账号继续按实际连接核验额度和收尾，补货核验同步跟踪实际分组。重新导入凭据保留本机归属，跨服务器迁移不携带外部补货锁，仍检查原下游身份。适用于现有单进程部署，不支持多实例共享同一 SQLite 同时调度。

金额按配置的每号保守成本预留记账，不是供应商实付账单，也不包括手动和旧策略支出。结果未知跨日仍占用预算；已提交失败成本保守保留，未提交撤销释放。卡片单号占用、累计开通上限及付款防重仍走原机制。

额度由独立 4-worker 队列采集，不阻塞并发采样；大池整轮刷新可能超过配置周期，过期样本不参与时间决策。决策按变化或每 30 秒存档，配置保存及熔断重置也留记录。保留天数仅清理决策快照；任务和订单保留用于防重。

## 验证

覆盖双规则取最大值、批量硬上限、在途冷却、提前到货缺口、额度重置和套餐变化、合法零负载与缺失过期数据、上游异常、逐号就绪、付款后恢复、未知结果找回原订单、原子领取预算、重启和迁移。浏览器验收使用本地假数据，不产生真实订单。

## 卡片准备等待与页面读取

卡片调度锁或 EJH 卡台繁忙时，单次全自动启动最多等待对应锁 2 秒，随后明确返回“尚未提交／等待准备”，不会一直占住操作按钮。补货监控不等待开卡准入锁；本轮暂不能领取或派发时继续更新快照，下一轮再判断。

EJH 原付款待核实、未知开卡或自动开卡失败冷却，属于资源准备等待。确认当前任务没有自己的付款、开卡或卡片预留证据后，仍用原任务、原账号和原预算排队，不增加失败数、不消耗新的换号次数。等待时间沿用 **Pro 全自动配置 → 高级设置 → 重试间隔（秒）**；实际在不早于该时间的下一轮补货调度执行。任务列表和详情显示原因及下次检查时间。原未知订单和卡片占用保留，必须核实；有自己的未决开卡／付款则继续走原核验路径，不能转回可重新提交的队列。

第二步换号的手动／定时接替准备等待也采用已配置的重试间隔。补货接替若在准备阶段确认终止，同时结束其“等待换号执行”标记；不会留下永远被扫描但无法派发的假排队。人工核实 EJH 开卡“确实未执行”会持久保存核实结果，不因核实更新时间再触发 5 分钟失败冷却；其他实际失败仍保留原冷却。

补货状态、历史记录、关联任务和兜底概览使用独立 SQLite 只读 WAL 视图，不排队等待业务写锁；卡片候选只读计算同样隔离，最终预留仍在事务内校验。决策表为时间倒序分页增加索引，保留全部原始详情；大响应支持 gzip。状态每 5 秒读取，历史每 30 秒独立刷新，后台标签停止这些轮询；首屏、保存结果和记录读取互不等待。读取设置 15 秒超时与重试入口，失败保留已显示数据。

## 手动全自动遇到卡台临时忙碌

手动全自动在选卡前遇到卡片调度锁或 EJH 操作锁忙碌时，页面保留本次账号和提交参数，每 3 秒重试一次，最多 30 次；期间可关闭窗口取消等待。请求被后台接受后仍按原后台流程执行，关闭窗口不影响已启动任务。

只有后台明确确认当前尝试尚未开卡、尚未付款的锁等待才可自动重试。每次重试核对原流程、订单及停止版本；账号已推进或已停止时取消旧重试并刷新进度。网络断开、开卡结果未知、付款待核实与其他业务错误不自动重复提交。自动补货继续使用原有持久任务和配置的等待间隔。

手动全自动的银行卡准备优先于后台同步、自动销卡/销卡轮询以及自动补货的新卡片任务。已发出的卡台操作先完成，再优先处理手动请求；等待重试之间保留 10 秒优先窗口，关闭页面后自动到期，避免长期阻塞定时任务。后台同步仍保留原任务排队，定时卡片操作在后续轮次恢复；不更改原刷新间隔、资金和卡片准入规则。

## Sub2 代理累计绑定上限

Sub2 / Sub2SIWC 的绑定代理列表同时显示当前绑定账号数、累计绑定次数和待确认次数。点击“保存上限”独立保存当前下游的统一上限，0 为不限制；同一 Space 实例中指向该下游的普通推送、Pro、SIWC 共用累计记录和限制。候选代理先排除未启用、过期、缺少绑定数量或累计额度已满的代理，再选择“当前绑定账号数 + 待确认预占次数”最少的代理；仅在这一组中选择“累计绑定次数 + 待确认预占次数”最少者，两项都相同时随机。上限为 0 时同样按此优先级选择。例如当前 0 个、累计 7 次的可用代理，优先于当前 2 个、累计 2 次的代理；当前数量相同才比较累计次数。每次新推送在同一下游共享锁内重新读取当前绑定数，待确认请求继续占位。人工修改累计次数后下一次新推送即使用新值；已提交但结果不明的推送仍沿用原代理、请求和幂等键，不调整既有账号的代理。

累计记录按规范化下游地址，以及代理的协议、主机、端口和用户名指纹保存，不使用代理名称或导入 ID；改名、删除账号、代理删除重导及重启都不会清零。代理密码不会参与标识，也不会返回浏览器。首次记录以当时现有绑定数为基数，之前已删除的历史无法还原，可通过每行“修改累计次数”补录或调整。人工修改持久保存并记录修改前后值；后台若已产生新绑定，旧编辑版本会拒绝覆盖。

绑定请求与名额预留原子持久化，确认成功后仅计数一次；网络超时和结果不明保留原请求、幂等键和预留，不重新选代理。已提交请求继续按原记录确认，即使后来下调上限。明确的首次请求参数/认证拒绝释放预留，不增加累计数。旧版本已经在途的推送保留原处理方式；累计计数不追溯推断未知历史。仅修改旧账号 OAuth 凭据、或关闭绑定代理时，不产生新绑定次数。
