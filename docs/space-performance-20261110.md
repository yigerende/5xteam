# Space 后台巡检、卡台并发与页面传输优化

## 已确认原因

正式实例有约 735 个邮箱，账号资料约 5.3 MB、加密凭据约 48 MB。旧额度巡检每秒、超时合并每 5 秒遍历全部账号并解密凭据，还在整个过程中持有共用 Store 锁。SIWC、补货和接管也有重复历史资料读取。短时 CPU 采样中这些路径合计占约 58%，服务器硬件没有饱和。

EJH 同步整轮约 35～40 秒持有卡操作锁，自动补货获取同一把锁仅等待 2 秒。合并入口另有不分页的完整 Pro 参考列表，约 7.9 MB；余额总览首次响应约 4.9 MB，已有 gzip 和增量响应，但外网传输仍耗时。

## 实施

- 额度、超时合并、SIWC、降智和补货供应候选先由 SQL 筛选，配套部分索引。只读取候选 profile，不解密账号凭据。保留 SIWC 独立观察、已停用账号排除供给、未完成移除及 VM2 清理；原执行条件和执行前复查继续生效。
- 只读筛选使用独立 WAL 快照。旧完整邮箱读取也移出共用业务锁，按管理范围先过滤，再保留原凭据状态推导和排序。接管根据实际下游编号查找账号，未推送统计只读对应候选。
- EJH 全量同步仍串行、同范围合并请求、最多四个不同范围任务。卡页和单卡交易之间释放操作锁；重新取得锁后读取当前卡分类及供应商身份，防止使用让锁前的旧状态。单卡网络查询与提交仍受原操作锁保护，不并发写同一张卡。
- 手动和自动准备银行卡都优先于后台维护；手动全自动继续优先于自动补货。已提交的操作完成后再让位。未知开卡/付款仍仅核查原单，不重付，不放宽正常分类、模板、预算或占用限制。
- 合并页面通过 `/api/pro-accounts/options` 只读取邮箱及 AT 状态；选中后的 AT 提取仍走原接口。完整 Pro 列表接口继续保留供已有调用方使用。
- gzip 使用标准压缩级别和复用压缩器，保留完整响应字段、权限、no-store 和增量协议。余额总览继续用原财务公式和全部历史输入，不改变成本、回款、余额或费用算法。

## 验证与边界

新增 1000 条历史账号、不可解密凭据、共用写锁占用下的候选查询和轻量选项测试；覆盖到期/未来/每日合并、自动流程、停止、VM2 清理、SIWC、历史排除、部分索引、取消上下文。新增同步中途自动准备抢占、分类改变后不再查询待定卡的并发测试。

已有相关 Store、卡台同步、模板、手动优先、补货、SIWC、额度/降智、列表压缩测试及前端类型、列表请求、EJH 页面/增量、财务公式、补货页面、选卡/重试/停止回归验证。旧选卡测试脚本没有加载已经拆出的提交函数，补全测试环境依赖后通过，未修改选卡页面业务代码。

Windows 扩大后的 HTTP 测试集合曾超过 420 秒总时限，超时时正在初始化下一测试的隔离管理员，不是业务请求挂死；不以此声称全仓测试通过。发布前仍执行目标用例及 Linux 隔离回归。没有正式开卡、付款或退款压测。

定时配置、重试次数、金额判断和正式数据保持原样。卡台单个上游请求仍可能受网络延迟影响，首次余额总览仍包含完整财务输入；本次不承诺任何页面无条件秒开。
