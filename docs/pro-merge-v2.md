# Pro 合并空间2.0

入口：Pro 全自动配置 → 空间合并/删除账户/API 商户/合并2.0 → 查额度达标后合并空间2.0。
与旧空间合并、删除账户、API 商户互斥；默认关闭，沿用目标母号、席位与合并并发配置。
额度达标、推送超时、降智处理、每日定点和手动续跑均可进入该流程。首页 AT 合并工具保持原协议。

## 独立流程

1. 母号邀请子号，保存母号、Team ID 和席位快照。
2. 使用原密码/TOTP/邮箱验证码及代理选择机制重新登录，明确选择目标团队。只在实际会话与 AT 的团队、邮箱一致时继续；临时团队 AT 不覆盖推送凭据。
3. 在同一 curl_cffi 会话、同一代理下发送 `POST https://chatgpt.com/backend-api/accounts/export_and_deactivate`。
4. 2xx 且 JSON `success` 为布尔 `true` 才保存受理；请求结果未知时进入下述独立套餐兜底，不伪造受理时间。
5. 执行原配置的下游分组调整或 vm2api 清理，完成本地流程。

提交没有请求体、没有 `chatgpt-account-id`，Bearer 为新团队 AT；Chrome impersonation，固定 Safari UA，Origin/Referer 均为 `https://chatgpt.com`，`oai-language: zh-CN`，超时 60 秒且不自动跟随重定向。每次提交前检查团队凭据获取时间小于 120 秒；超时、时间未知、明确的 `invalid_workspace_selected` 会通过原有有界登录重试重新建立会话。换出口时重新登录，绝不复用旧出口的团队凭据。

## 恢复与停止

邀请已发送不等于已加入。若 2FA 后直接返回普通回调并得到个人 AT，先验证子号身份，再用本轮子号会话读取账号列表：目标团队已存在则进入有限次数重新登录；不存在则通过已有 `POST /backend-api/accounts/{目标团队}/invites/accept` 接受邀请（空 JSON、目标 `chatgpt-account-id`，仅用于接受邀请，不用于停用请求）。发送前在 Go 端检查邀请成功、原目标、停止状态并持久化一次接受检查点；网络结果不明仅读取成员关系核实，不重发接受邀请。明确接受或成员关系核实成功后重新登录，绝不拿原个人 AT 提交停用。接受未知或身份不符时停止并保留现场。

团队会话不匹配时，默认额外重新登录 **2 次**，每次间隔 **5 秒**（首次加恢复最多3次团队登录）。仅子号身份已核实、尚未提交停用时进入这项恢复；沿用原登录及目标团队选择机制，每次重建协议进程、登录会话；同一流程复用加密保存的代理会话，不重邀、不换子号、不重做开通。密码/身份错误、死号及提交结果未知不走此恢复。网络重试仍由原OAuth机制独立负责；恢复次数用尽后保留团队成员并报错，不随监控轮询无限重试。等待期间响应停止操作。默认值位于 `internal/httpapi/pro_merge_v2_login.go`。

登录返回缺少下一步时，按「Pro 全自动配置 → 高级设置 → 其他步骤失败重试次数 / 重试间隔（秒）」有限重试。另一个可恢复情况是：初始提交邮箱后、尚未验证密码时，响应明确选择 `email_otp_verification/passwordless_login`，但账号配置为密码和 TOTP 且没有收码链接。此时重新发起原账号的普通登录，仍须通过上游密码、MFA、身份和团队校验；重试次数为额外次数，0 表示不重试。这个预算与团队不匹配的2次恢复分别计数，内层不立即重复重试或轮转代理。

密码验证后追加的邮箱验证码、未知安全挑战不适用上述登录方式恢复。已有收码来源仍正常查收并提交验证码；没有来源或未收到验证码会显示明确原因。每轮保留邀请、原团队及固定代理，检查停止、死号、已提交与已受理状态；等待、次数耗尽及错误码写入原异步诊断记录。

合并2.0登录详细记录接入现有异步审计队列：记录执行ID、团队登录轮次、网络轮次、HTTP状态、请求路径、回调分支、团队选择是否发生、AT/Session团队是否匹配、身份是否匹配及重试决定。账号日志及导出可查看；不保存密码、AT、Cookie、原始请求/响应体或回调查询参数。数据库落盘不阻塞登录流程；队列溢出沿用审计丢弃计数及日志告警，导出会报告缺失，不能承诺强制终止进程时内存记录零丢失。

发请求前先持久化提交检查点。网络中断、5xx、2xx 无严格成功字段均为结果未知：先保存未知检查点，不直接重复提交；按下方套餐兜底处理。明确 4xx 拒绝才能清除检查点。已受理仅续跑移出和下游处理，配置切换不改变已启动的 2.0 流程及团队。

原“停止全自动”同时停止独立 2.0 流程和等待中的请求；已发出请求不能撤回，已受理的事实保留。重启后保留进度及恢复预算，后台按保存的时间继续核验；账号停止或全自动最后一步暂停时不自动入队。状态列支持逐步手动核实，提交结果未知时必须明确确认“未受理”才能重置并再次提交；已受理检查点和已完成流程不能重置重发。状态修改不会直接发上游请求。

本地“完成”表示提交已受理或个人套餐已严格核验为 Free，并且成员已移出、下游处理已完成，**不等于上游个人空间停用完成或退款到账**。没有增加商户收费；两卡台继续按实际回款核实。EJH 仅记录退款申请待核实，不伪造到账。

## 验证

- Python 离线协议测试：请求头/无请求体、同会话、目标团队/邮箱、120 秒、严格成功、拒绝与不明结果、停止检查点。
- Go 模拟上游测试：完整自动尾流程、旧凭据不变、停止/续跑、结果未知与重启、模式锁定、手动修正、互斥配置、独立筛选。
- 浏览器隔离页面：`frontend/scripts/pro-merge-v2-preview.html` 与 `check-pro-merge-v2-browser.js`，禁止真实外部请求。

停用提交同样写入异步结构化诊断：开始时间、HTTP 状态、耗时、curl 错误码、异常类型与脱敏错误；不会保存 Bearer、请求体、Cookie 或原始响应。未知提交仍保留检查点，具体协议结果不再被通用待确认错误覆盖。

停用请求继承登录 Session 的固定 Chrome TLS 配置，不再单独覆盖成浮动的 `chrome` 别名，避免因 TLS 参数变化主动另建动态代理连接。仍保持原代理、Safari 请求头、无请求体和60秒超时；连接被远端关闭仍可能中断，不能据此断言所有 curl56 都来自 TLS 配置。邀请接受失败另外保存受限格式的错误码、错误类型、HTTP状态和耗时，网络异常保留 curl 数字错误码；不保存错误正文。接受结果未知仍只查询成员关系，不自动重复提交。

## 结果未知后的套餐兜底（2026-10-29）

参考回序的移出后套餐核验，设置位于 Pro 全自动配置 → 空间合并/删除账户/API 商户/合并2.0 → 合并2.0 · 移出后套餐核验。默认启用、间隔30秒、最多2轮、每轮3次；设置可关闭或修改。初始未知结果与历史未完成未知结果先持久化下次时间，不立即执行恢复。

每次后台任务只执行一次核验：使用原母号代理，核实原团队内匹配子号邮箱、用户ID与普通成员角色后移出；完整分页复查成员和邀请列表，空响应、分页冲突、401或身份不符不能当作移出成功。随后释放母号锁，使用加密保存的原子号代理会话重新以密码/2FA登录个人空间，验证Session、AT邮箱及用户ID、实际 `/me` 邮箱和个人account ID，再读取真实套餐。

- 明确 Free：保存 `completion_basis=plan_free`，保留原SubmittedAt且不写AcceptedAt，直接执行原单后续分组/清理。页面提交步骤显示“套餐确认”；卡台回款仍由真实流水决定。
- 明确付费：保存原提交历史和下一次执行时间，同一账号、团队、订单重新排队邀请办理，不重新开通或付款。达到轮次上限停止，不再重复提交。
- 请求失败、身份不明、套餐冲突或数据缺失：保留移出检查点和错误，按间隔继续核验，不回退到已完成操作。每次核验最多4分钟，每轮最多配置次数；超限展示人工处理。停止和重启不清零预算。

等待时没有持有母号锁、并发执行名额或长时间sleep。个人套餐核验不占母号锁；下游分组也释放母号锁。协议证据继续异步写入原账号日志，列表显示恢复阶段、次数、下次时间和完成依据。代理URL单独加密保存，不进入列表或浏览器响应；旧流程若此前未保存代理快照，首次恢复使用当前OAuth配置并固定供后续恢复使用。
