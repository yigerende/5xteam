# 换号补货完成与原单核实分离

第二步付款结果待核实后，现有流程可能已经为替换账号完成付款、推送和监控核验。原任务仍为 unknown，原先被一并算入补货在途，导致批次永久等待。

现在只沿数据库已有的换号关联确认结果：原流程 ID 对应的 recharge 任务、下一账号、前后邮箱、根账号、同一决策、创建先后必须一致；末端任务必须已 ready、有实际核验时间和下游账号 ID，且对应付款记录为 success。查找有 64 层上限及重复节点保护，不发上游请求，也不扫描全部邮箱凭据。缺少任一证据则继续保留在途。

确认后仅在原补货任务记录 fulfilled_by_task_id、fulfilled_by_email、fulfilled_at。页面显示“换号补货成功”和替换账号、实际完成时间，不再算作在途；新一轮仍需完成后的监控采集才允许预留。连续换号的多个祖先都由同一末端成功任务完成，不重复计入新增容量或补货耗时样本。

原订单状态、付款核实记录、卡片占用、费用及账号信息不变。unknown 的预算保留规则不变，不能借补货成功宣称原单付款失败或释放原卡。页面提示到开通订单查看原核实记录。超过 48 小时的已交付祖先不再永久进入监控热列表，决策历史仍可查看。

使用数据库事务及原始 payload 比较防止旧观察覆盖并发修改；先完成的停止操作不会被改回成功，重复核验不更新完成时间。无新增付款、开卡、换号或真实付费测试。

原账号被删除时，使用原任务绑定的实际付款单验证 `pro-auto-流程ID`，再读取准确的 `recharge:流程ID` 后继任务，仍要求其账号的前驱邮箱、根账号、决策及付款/就绪证据一致，不以账号删除直接判断付款失败。

卡台人工核实或删除未开通回款记录时，同一原订单的 unknown/attention 补货观察不再被误认为执行中的工作。账号实际执行、其他订单/预留任务、上游执行中或已付款证据仍阻止错误释放。操作员明确确认后，在同一事务结束该原单的补货等待并记录核实依据，释放仅限该订单；保留原请求、供应商响应和历史资金记录。重试幂等，不能解除新订单占用。

验证包含成功及多次换号、未知/失败付款、核验信息缺失、错误关联、停止竞争、8 路重复核验、重启恢复、下一批新鲜监控门槛、历史读取及预算保留，以及前端在途/成功筛选、时间与说明展示。
