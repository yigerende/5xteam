# Pro 开通与完整自动流程（GPTPay）

提供独立的“开通 Pro”按钮和“全自动开通 Pro”按钮。

## 使用

1. Pro 管理 → Pro 全自动配置：保存 GPTPay API 地址、API Key 和 Pro 5x / Pro 20x。
2. 银行卡信息：添加并启用银行卡。可粘贴 `银行卡号----202812----CVV`，解析后核对年月。支持 YYYYMM、YYYY-MM、YYYY/MM、MM/YY、MM/YYYY；四位连续年月为 YYMM。
3. Pro 账号：点击“登录获取 RT / AT”前的“开通 Pro”，选择银行卡并确认。
4. 窗口显示受理、处理中、成功/失败等状态。GPTPay 供应商 tab 可查询账户余额、套餐费用、订单结算、失败原因和取消续费状态。

## 供应商协议

来源：<https://gptpay.tokenseek.app/docs>，2026-09-21 核对。
供应商公开页面脚本确认套餐代码为 `pro5`（Pro 5x）、`pro20`（Pro 20x），`plus` 为另一个套餐。

- `GET /api/v1/user`：查询账户及可用套餐；HTTP 请求头 `X-API-Key`。
- `POST /api/v1/gpt-recharge/orders`：创建订单；请求头 `X-API-Key`、`Idempotency-Key`、`Content-Type: application/json`。
- `POST /api/v1/gpt-recharge/orders/status`：请求体 `{"orderIds":["供应商订单ID"]}`，每次 1～50 个 ID。

开通请求体为 `planCode`、`cardNumber`、`expMonth`、`expYear`、`cvv`、`session`。Session 仅包含 `user.email`、`account.id`、`accessToken`，使用账号保存的 AT；本功能不登录、不刷新 RT，也不改写账号 AT/RT。Account ID 优先从该 AT 提取，其次使用与 AT 匹配的保存 Session，最后使用账号保存的 OAuth Account ID；缺少或 AT 已过期会阻止提交。

HTTP 201/200/202 且业务 `code=0` 只代表供应商受理。最终开通结果以订单 `status` 为准；`success` 即更新开通阶段成功，取消续费失败或等待不影响后续步骤。取消续费结果单独显示。

后台同步不依赖弹窗：每 5 秒扫描最多 20 笔到期订单，最多 2 个并发查询。首分钟每 5 秒、之后每 15 秒同步；开通已结束但取消续费仍等待/处理中时每 60 秒同步。查询失败单独记录并退避 60 秒，不覆盖原开通状态。下一次查询时间持久化，关闭弹窗、切换页面、服务重启均会继续。正在全自动流程内的账号由原会话任务负责查单，后台跳过；手动刷新与后台同步共用账号锁。后台只查询已有供应商 ID 的订单，使用该订单原保存的供应商地址与密钥，不重复提交开通。

## 订单恢复及存储

配置、银行卡、订单均持久化 SQLite。API Key、完整卡信息以及用于原单恢复的请求快照采用项目主密钥加密，列表和日志不返回 AT、完整卡号或 CVV。备份时数据库与主密钥需一同保留。

发起付款前先保存订单及原始请求。每个账号同一时间仅允许一笔未结束订单，使用账号互斥锁和数据库唯一索引保护。超时、5xx、无法确定提交结果或服务重启后，保持原订单为待确认，不自动创建新单；“重试原订单”使用原幂等键与完整原参数，即使之后编辑卡、切换套餐或更新 AT，也不会改变已经提交的请求。已返回供应商 ID 的订单仅查询，不重新提交。

开通按钮再次打开会先显示已有订单。已结束订单需要显式选择“新建开通”才能进入下一次确认。供应商 `not_found` 或未知状态不会把进行中的本地订单当成已结束释放。

## 验证

- Go 模拟 HTTP 接口：完整请求字段、HTTP/业务双状态、并发重复点击、不可用卡、过期 AT、幂等恢复、终态保护。
- SQLite 测试：加密字段、服务重启恢复、未完成订单唯一约束。
- 浏览器隔离页：`frontend/scripts/gptpay-preview.html`；验证脚本 `check-gptpay-browser.js`，拦截所有业务请求，不进行真实扣费。
- 前端解析/轮询测试：`node frontend/scripts/check-gptpay.mjs`。

真实供应商开通需要用户配置有效 API Key、可用银行卡和账号 AT。自动化测试不产生真实充值订单。

## 全自动流程

“合并空间选择”菜单已并入“Pro 全自动配置”。开通套餐、供应商、会话时长、额度阈值/间隔、目标母号、席位类型、并发、重试统一在该页保存。额度阈值和间隔仅存于 `pro_settings`；GPTPay 配置不再另存额度设置。普通 Pro 检测使用相同阈值（不再写死 100%），新全自动任务从这里生成配置快照，已启动任务不受变更影响。开通套餐和空间席位套餐是不同用途，分别保留。

保存使用 `/api/pro-settings/automation`，同一数据库事务提交开通和合并配置，不覆盖推送地址、密码或分组。升级时保留原阈值；检测间隔优先保留原已启用的 Pro 定时检测间隔，否则采用原全自动间隔。原定时检测及自动合并开关保留，用于其他已推送的 Pro 账号；完整全自动任务仍独立推进自身流程。

“全自动开通 Pro”在没有 AT 时也可点击。先在 Pro 全自动配置中选择套餐、7 天已用额度阈值（默认 100%）、额度检查间隔（默认 120 秒）、登录及开通会话最长保留时间（默认 30 分钟），并配置 Pro 的 Sub2 推送与合并目标母号。点击账号按钮后选择银行卡并确认启动。

阶段列位于原四步状态之前，显示：登录 → 开通 → RT/AT → 推送 → 额度 → 合并。合并阶段复用现有邀请、进入、合并、移出四步流程及日志、母号代理、串行控制。

首次登录复用现有 `ProjectProtocolLogin` 的 Web AT 登录逻辑。新入口 `protocol_pro_auto.py` 保留同一个 Python 进程、curl_cffi Session、Cookie、设备标识及代理租约；通过本地 stdio 通知 Go 用 AT 向 GPTPay 开通并等待结果。GPTPay 无需浏览器会话，也不接收代理配置。

开通成功后，第三步使用原 Python 会话继续生成 Codex PKCE 授权、处理 consent/callback、交换新 AT/RT，再读取最新 Web Session。所有这些请求仍由原 curl Session 发出，不再次提交邮箱、密码或验证码。新 RT/AT/Session 保存完成后才关闭该会话、释放代理，再推送 Sub2。原有单项登录按钮的逻辑保持不变。

从首次登录前开始，同一个 curl Session 会在登录前两次、第一步登录完成、第三步开始、每次交换 RT/AT 前、保存新 RT/AT/Session 前查询出口。首次拿到的有效 IP 作为基准写入本次任务数据库，后续始终比较该基准，不会用变化后的 IP 覆盖。供应商开通使用独立供应商接口，只保留原 GPT 客户端等待，不检测或比较供应商的 IP/客户端。

另外保存第一步登录完成时的出口快照。第三步开始、凭证获取完成、凭证保存完成分别记录与第一步的直接对比：`initial_client_id`、`client_id`、`client_consistent`、`login_exit_ip`、`oauth_exit_ip`、`ip_consistent`，以及是否重新登录、凭证是否保存。客户端一致性基于实际 curl Session 对象身份判断；IP 检测失败时标记“无法判断”，不把缺失值当成一致。日志不包含 Cookie、Session 或 Token 的实际内容。

IP 检测仅用于记录：不一致标记“changed”，查询失败或没有有效 IP 标记“unavailable”，不会因此中止、换代理 session、重新登录或重复开通。继续沿用原客户端执行开通、获取并保存新 RT/AT、推送等后续任务。全自动 Pro 不再经过原独立 OAuth 的出口拦截入口；原独立登录/重登的规则保持不变。登录、供应商付款、OAuth 本身的失败、用户停止及总任务超时仍按原规则处理，不能把真实失败当成成功。

等待额度期间不占用 Python 会话和并发名额。只从数据库读取已到检查时间的自动任务，每次最多 20 条，使用已有 Pro 并发上限。达到本次任务保存的 7 天已用阈值后执行四步合并；旧 Pro 定时器不会重复处理这些任务。

阶段与订单 ID 持久化保存。关闭网页不终止后台任务；可在进度窗口停止。停止本项目流程不会取消供应商已受理的订单。服务重启不能保留内存里的登录会话：若新 RT/AT 尚未取得，标记中断并保留原单供核查；若 RT/AT 已保存，可以点击“继续后续流程”，不会再次登录或付款。付款前失败且没有创建订单时可重新启动。

自动流程运行期间会拒绝同账号的冲突操作。不同账号使用独立会话；同账号重复点击只启动一个任务。窗口与账号全流程日志可查看阶段、错误和代理名称。

自动流程新增验证：`python internal/test_protocol_pro_auto.py`（邮箱验证码、密码 + TOTP、邮箱验证码后 TOTP 的同一 curl 客户端贯穿登录、付款等待、PKCE 与 token 交换；各阶段出口漂移或查询失败继续完成，真实会话失效、付款不确定仍停止），以及 `TestProAuto*` 后端并发、阶段推进、等待额度、阈值、断点恢复测试。页面验证脚本为 `frontend/scripts/check-pro-auto-browser.js`。
